`fsync()` on a file makes *that file's* bytes durable. It says nothing about the name the
file is reachable by, nothing about the order your other writes land in, and nothing about
what a crash leaves on disk halfway through. Every engine that replaces a file in place —
RocksDB's `CURRENT`, Postgres's WAL segments and `pg_control`, SQLite's rollback journal —
encodes the same four-step protocol because the filesystem below it is allowed to reorder
almost everything else.

Load **"Write temp + rename, no fsync"** and step the filesystem selector from
`ext4 data=ordered` to `XFS`. Nothing about the program changed; the number of legal
post-crash disk images went from 5 to 8, and two of the end states they produce —
`zero-length file` and `right size, zeros` — are corrupt. That difference is
not a bug in either filesystem. It is the difference between what they promise.

## What the filesystem actually promises

POSIX gives you exactly one durability primitive and one atomicity primitive:

- **`fsync(fd)`** — when it returns successfully, the data *and* the inode metadata of that
  open file are on stable storage. `fdatasync(fd)` is the same minus metadata that is not
  needed to read the data back; because `i_size` *is* needed, an appending write still forces
  an inode update, which is why `fdatasync` only helps for overwrites in place. Postgres's
  default `wal_sync_method` on Linux is `fdatasync` for exactly this reason.
- **`rename(old, new)`** — the target name atomically refers to either the old inode or the
  new one, never to nothing and never to a mixture. This is *namespace* atomicity. It says
  nothing about whether the new inode's blocks reached the platter.

Everything else is unspecified. There is no ordering between two writes to different files,
none between a write and a rename, and no guarantee that the directory entry naming a
newly created file is durable just because the file itself is. The OSDI '14 paper *All File
Systems Are Not Created Equal* (Pillai et al.) tabulated these "persistence properties"
across ext2/3/4, btrfs and others and then found real bugs in LevelDB, Git, Mercurial, HSQLDB
and ZooKeeper caused by assuming properties one filesystem happened to provide.

:::caution[The two illusions]
"My writes hit the disk in the order I issued them" and "the file exists because I created
it" are both false. Issue order survives only where a journal or a copy-on-write transaction
makes it survive, and a file's existence is a property of its *parent directory*, which is a
different object with its own dirty state.
:::

## Journaling modes decide which orderings survive

A journaling filesystem writes a description of a change to a log, waits for that log record
to be durable, and only then modifies the real structures. Recovery replays or discards whole
transactions, so metadata is never half-applied. What differs between filesystems is how much
goes into the journal and whether file *data* is ordered against it.

| Filesystem / mode | In the journal | Data vs metadata ordering | Cost |
|---|---|---|---|
| ext4 `data=journal` | metadata **and** data | Atomic together, in issue order | Every byte written twice; ~half the throughput |
| ext4 `data=ordered` (default) | metadata only | Newly allocated data blocks are flushed **before** the transaction that exposes them commits | Small; one extra ordering dependency per transaction |
| ext4 `data=writeback` | metadata only | None. A rename can commit before the bytes it points at exist | Fastest, and the mode that produces surprises |
| XFS | metadata only (delayed logging / CIL) | None — but unwritten extents read back as zeros, never as another file's deleted data | Fast; excellent metadata scalability |
| btrfs / ZFS | nothing is overwritten in place | A transaction group (btrfs ~30 s, ZFS ~5 s txg) publishes a new tree root atomically | Write amplification, fragmentation |

ext4's journal is `jbd2` and it commits every `commit=5` seconds by default, in strict
sequence numbers. That sequencing is why the puzzle's metadata column behaves as a *prefix*:
on ext4 and XFS a later metadata change cannot be durable while an earlier one is not, because
they share one ordered log. On btrfs and ZFS the prefix covers data too — a crash lands you
exactly on some past commit, never on a mixture — which is why the copy-on-write column in
the puzzle never produces a torn or exposed state.

`data=ordered` is worth understanding precisely, because it protects less than its name
suggests. It orders data that is *exposed by new metadata* — newly allocated blocks. Overwriting
existing blocks of an existing file allocates nothing, so there is no metadata to order against
and no protection at all. Load the **"Overwrite in place"** plan, set the crash point to step 2,
and you will see `half old, half new` appear even on `data=ordered`.

## Delayed allocation and the zero-length file

ext4, XFS and btrfs all do **delayed allocation**: `write()` dirties pages in the page cache
and does not choose physical blocks at all. Allocation happens at writeback — up to
`dirty_expire_centisecs` (default 3000, i.e. 30 s) later — so the extent map and `i_size` that
make the bytes findable are created *after* the rename you issued was already on its way to the
journal.

That is the 2009 ext4 data-loss story (Ubuntu bug #317781): applications did
`write(tmp); rename(tmp, real)` with no fsync, crashed, and found **zero-length** config files.
On ext3 `data=ordered` the same code had been accidentally safe for years, because ext3 had no
delayed allocation and flushed data every 5 seconds. ext4 broke the accident, not the contract.

Ted Ts'o's fix was a heuristic, not a guarantee: since 2.6.30 ext4 mounts with `auto_da_alloc`,
which forces the delayed allocation out when you `rename()` over an **existing** file or
`open()` an existing file with `O_TRUNC`. Two things follow, and both are visible in the puzzle:

- On `ext4 data=ordered`, replacing an existing file with an unsynced rename is safe (5 legal
  images, all of them old-or-new) — but switch the target to **brand-new file** and the
  protection vanishes, because there was no existing inode to trigger the heuristic. Zero-length
  is back.
- The heuristic starts writeback; it does not issue a cache flush. Your data can still be lost
  to a power cut, just not *corrupted*. `mount -o noauto_da_alloc` restores the 2009 behaviour,
  and `auto_da_alloc` is an ext4 mount option — nothing in POSIX obliges another filesystem to
  offer the same heuristic, so portable code cannot lean on it.

## Why a new or renamed file needs `fsync` of the parent directory

A file is two objects. The inode holds the data and `i_size`; the **directory entry** that maps
the name to the inode number lives in a *different* inode's blocks. `fsync(fd)` covers the first
and not the second. So after

```c
fd = open("wal/000000010000000000000042", O_CREAT|O_WRONLY, 0600);
write(fd, buf, 16 * 1024 * 1024);
fsync(fd);                 /* the 16 MB are durable … */
```

a crash can leave you with a perfectly durable inode that **no name points to**. It is not lost
data; it is an orphan the next `fsck` or the orphan-inode list will reclaim. You need

```c
dirfd = open("wal", O_RDONLY|O_DIRECTORY);
fsync(dirfd);              /* … and now the name is durable too */
```

Set the puzzle's target to **brand-new file**, pick `POSIX minimum`, load **"fsync file, then
rename"** and crash after the last step: `still missing` is a legal outcome. Add `fsync dir` and
it disappears.

On ext4 and XFS you will usually get away without it, because any `fsync` forces a log flush and
their single ordered log carries every earlier metadata change with it — including your dirent.
That is an implementation accident of a shared journal, not a promise, and it does not hold on
every filesystem, on every mount option, or on NFS. The directory `fsync` is cheap and the bug it
prevents is unfalsifiable in testing.

## The safe-replace protocol

Four steps, in this order, are the only sequence that is atomic *and* durable on every mode in
the puzzle:

```c
/* 1. write the new contents to a sibling temp file */
int fd = open("app.conf.tmp", O_CREAT|O_WRONLY|O_TRUNC, 0644);
write_all(fd, buf, len);

/* 2. force the bytes AND the extent map to stable storage */
if (fsync(fd) != 0) abort_and_report();   /* see: fsync can fail once, and only once */
close(fd);

/* 3. atomically swap the name — same directory, same filesystem */
if (rename("app.conf.tmp", "app.conf") != 0) abort_and_report();

/* 4. make the directory entry itself durable */
int dirfd = open(".", O_RDONLY|O_DIRECTORY);
fsync(dirfd);
close(dirfd);
```

Each call is load-bearing:

- **Temp file, then rename** — never truncate the original. `O_TRUNC` is a metadata change that
  can commit alone, which is the `zero-length file` row in the puzzle and is corrupt on *every*
  filesystem including btrfs.
- **`fsync` before the rename, not after.** Move the fsync after the rename (the
  "Rename first, fsync after" plan) and set the crash point to step 3: on XFS and under POSIX
  minimum the rename can be durable while the bytes are not — a right-sized file full of zeros.
- **Same directory.** `rename` cannot cross filesystems, and putting the temp file in `/tmp`
  turns the whole thing into a non-atomic copy.
- **`fsync` the directory once, after the rename.** It covers the creation of the temp name and
  its removal by the rename in one call.
- **Check every return value, including `close()`.** On a delayed-allocation filesystem the
  write error may not surface until writeback, and a failed `fsync` marks the error *consumed* —
  the second call returns success on a kernel older than 4.13 even though nothing was written.

:::danger[There is no ordering primitive except a flush]
Nothing you can do at the syscall level orders two writes except making the first one durable.
The page cache coalesces adjacent dirty pages, the I/O scheduler merges and reorders requests,
NCQ lets the drive complete them out of order, and the drive's volatile write cache acknowledges
before anything reaches the media. Linux removed explicit write barriers in 2.6.37 and replaced
them with `REQ_PREFLUSH`/`REQ_FUA`, which `fsync` issues — mounting ext4 with `nobarrier`
(`barrier=0`) suppresses them and quietly converts every fsync into a lie.
:::

## How real engines encode this

| Engine | The file being replaced | What it does |
|---|---|---|
| PostgreSQL | WAL segments, `pg_control`, `pg_logical` state | `durable_rename()` in `src/backend/storage/file/fd.c`: fsync old, rename, fsync new, fsync the parent directory. `durable_unlink()` does the same for deletes |
| PostgreSQL | `pg_control` | One 8192-byte write protected by a CRC — a torn write is *detected*, not prevented: `"incorrect checksum in control file"` and the cluster refuses to start |
| SQLite | `-journal` rollback journal | Creates the journal, fsyncs it **and its directory**, then modifies the database; commit is deleting that journal file, and the delete must be durable — hence a second directory fsync (`SQLITE_DISABLE_DIRSYNC` turns it off) |
| RocksDB | `CURRENT`, which names the live MANIFEST | `SetCurrentFile()`: write `CURRENT.tmp`, fsync, rename to `CURRENT`, then `Fsync` the DB directory. New SSTs are fsynced and the directory synced before the MANIFEST references them |
| InnoDB | tablespace pages | Doublewrite buffer (`innodb_doublewrite`) for torn pages; `innodb_flush_method=O_DIRECT` bypasses the page cache but not the need to fsync a directory when a `.ibd` file is created |

SQLite's rollback journal is the clearest illustration of why directory durability is not
optional. The commit point of a transaction in `journal_mode=DELETE` is the *unlink of the
journal file*: on restart, a database with a hot journal next to it is rolled back, and one
without is considered committed. That decision is made purely from a directory entry. If the
unlink is in the page cache when the power fails, a committed transaction is rolled back. If
the journal's creation is not durable before the database pages are modified, recovery has
nothing to roll back with and the file is corrupt — `database disk image is malformed`.

Postgres inverts the emphasis. The WAL is append-only, so the interesting renames are
administrative: recycling a WAL segment installs it under a new name with `durable_rename()`,
and `pg_control` is rewritten in place on every checkpoint. Because `pg_control` is a single
page with its own CRC, Postgres does not need the filesystem to make that write atomic — it
needs only to *notice* if it was not. That is the general escape hatch: when you cannot get
atomicity from the filesystem, get detection from a checksum and recovery from a log.

## Where it bites in production

- **Zero-length or truncated config after an unclean shutdown.** Almost always a writer that did
  `truncate + write` or an unsynced rename. Symptom on Postgres: `could not read file
  "global/pg_control"` or a config file that parses as empty. Fix the writer, not the filesystem.
- **`nobarrier` / `barrier=0` mounts, and virtualised disks that ignore FLUSH.** The engine does
  everything right and the stack throws it away. Test with a real power cut or with
  `dm-log-writes`; `diskchecker.pl` and Postgres's `pg_test_fsync` will tell you whether your
  fsync is plausibly hitting media (a 7200 rpm disk that reports more than ~120 fsyncs/s is
  caching).
- **Container overlays and network filesystems.** overlayfs `rename` of a lower-layer file
  triggers a copy-up; NFS makes `fsync` a round trip whose ordering depends on the server's cache
  policy. Neither gives you the ext4-shaped accidents you have been relying on.
- **Deferring the directory fsync to "batch it later".** Legitimate — Postgres's `initdb
  --sync-only` and `recovery_init_sync_method=syncfs` exist precisely to sync a whole tree cheaply
  — but only if nothing treats the rename as committed before that batch completes.

| Knob | Where | Effect |
|---|---|---|
| `data=ordered\|writeback\|journal` | ext4 mount | Which orderings survive a crash (the puzzle's first control) |
| `auto_da_alloc` | ext4 mount, default on | Flush delayed allocation on rename-over and `O_TRUNC` |
| `barrier` / `nobarrier` | ext4 mount (XFS dropped the option in 4.19; its flushes are unconditional) | Whether fsync issues a device cache flush at all |
| `dirty_expire_centisecs` (3000), `dirty_background_ratio` (10) | `/proc/sys/vm` | How long unsynced data can sit in the page cache |
| `commit=5` | ext4 mount | jbd2 journal commit interval |
| `fsync`, `wal_sync_method`, `data_sync_retry` | postgresql.conf | Whether and how Postgres forces; whether an fsync failure panics |
| `PRAGMA synchronous`, `SQLITE_DISABLE_DIRSYNC` | SQLite | Number of sync points per commit; whether directories are synced |

:::note[What to take forward]
A filesystem gives you two primitives — `fsync` makes one file's bytes and inode durable, and
`rename` makes a name change atomic — and orders nothing else unless its journaling mode happens
to. Replacing a file safely therefore takes four calls in one order: write a temp file, `fsync` it,
`rename` it over the target, `fsync` the parent directory. Everything else, including truncate-and-
rewrite and unsynced renames, has a legal post-crash state that loses your data, and which
filesystem you are on only decides how often you meet it.
:::
